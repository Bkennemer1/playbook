<div className="step-page-section">
  <h2>Overview</h2>
  <p>The file comes back from underwriting <strong>Approved with Conditions</strong> — the loan is approved, subject to a list of items that must be satisfied before Clear to Close. This is the normal outcome; a first-pass approval with zero conditions is rare.</p>
  <p>Everything in this phase runs off one job at the top: <strong>the processor reads the approval letter and works every condition</strong> — borrower-facing and back-office alike. Get the list entered and tracked right and the file moves. Miss a condition, or leave one unowned, and it sits while the closing date approaches.</p>
</div>

<div className="step-page-section">
  <h2>Where conditions live</h2>
  <p>Two places, and the distinction matters:</p>
  <ul>
    <li><strong>The lender portal is the source of truth.</strong> Underwriting posts conditions there. That's the authoritative list, and it's what has to be satisfied to get CTC.</li>
    <li><strong>Arive is the working copy.</strong> The processor manually types each condition into the Arive Conditions tab. That's where status gets tracked and documents get attached.</li>
  </ul>
  <p>Manual mirroring means the two can drift. If a condition exists in the portal but was never entered in Arive, nobody's working it — and it won't surface until resubmission gets rejected.</p>
</div>

<div className="step-page-section">
  <h2>The processor's triage</h2>

  <h3>1. Read the approval letter in full</h3>
  <p>Every condition, start to finish, before working anything. Conditions frequently reference each other, and reading them as a set tells you which ones are actually one item split across two lines.</p>

  <h3>2. Enter each condition into Arive</h3>
  <p>Manually, in the Conditions tab. This is data entry with consequences — a condition typed vaguely is a condition someone misinterprets three days later.</p>

  <h3>3. Categorize</h3>
  <p>Each condition falls into one of five buckets. The bucket tells you <em>how</em> to work it — the processor owns all of them except decisions only the LO can make:</p>
  <ul>
    <li><strong>Borrower documents</strong> → collect from the borrower</li>
    <li><strong>Title</strong> → work with the title company</li>
    <li><strong>Appraisal</strong> → work with the appraiser / AMC</li>
    <li><strong>Income</strong> → the processor collects; route to the LO if it needs an income decision</li>
    <li><strong>LO decision</strong> → the LO on the file (structure, program, or qualification calls)</li>
  </ul>

  <h3>4. Set ownership in Arive</h3>
  <p>Mark each condition's owner in Arive. Most are the processor's to work. For any condition that needs an LO decision, assign it to the LO — <strong>Arive automatically emails the assignee</strong> the list of conditions that are theirs. That email is the handoff to the LO.</p>

  <h3>5. Flip the milestone</h3>
  <p>The processor manually updates the Arive milestone to <strong>Approved w/ Conditions</strong>.</p>
</div>

<div className="callout warn">
  <strong>Track every condition in Arive — don't work the list from memory.</strong> It's tempting to run a short condition list off a sticky note or your head. Don't. Enter every condition in Arive and keep its status current: it's the only record if you're out sick, if the file grows, or if someone else has to pick it up. A condition that lives only in your head is a condition that gets missed — and it won't surface until resubmission is rejected.
</div>

<div className="step-page-section">
  <h2>The condition status ladder</h2>
  <p>Every condition in Arive moves through a status progression. Knowing where each one sits is how you know whether the file is ready to go back to underwriting:</p>
  <ul>
    <li><strong>Requested</strong> — the condition is entered and the document has been asked for</li>
    <li><strong>Re-requested</strong> — what came back didn't satisfy it; asked again</li>
    <li><strong>Collected</strong> — the document is in hand, pending review</li>
    <li><strong>Ready to send</strong> — reviewed, satisfies the condition, cleared to go back to UW</li>
  </ul>
  <p><strong>Every condition must reach "Ready to send" before anything is resubmitted.</strong> That's the gate — see the resubmission step.</p>
</div>

<div className="step-page-section">
  <h2>What happens next</h2>
  <p>The processor works the conditions across two tracks — <a href="/phases/uw-decision/borrower-conditions">borrower-facing collection</a> and <a href="/phases/uw-decision/docs-and-arive-conditions">back-office items</a> — until all conditions are marked ready to send. Then the processor packages the file and resubmits.</p>
  <p>Expect roughly <strong>one additional round</strong> on a typical file: resubmit, underwriting reviews, a few new or re-requested conditions come back, clear those, resubmit again, then Clear to Close.</p>
</div>
